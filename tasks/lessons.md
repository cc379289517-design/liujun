# Lessons

- `launchctl load` 返回不代表 Next 服务已经开始监听端口；一键部署健康检查必须做短间隔重试，否则会出现服务实际启动成功、脚本却误报失败。
- Mac mini 通过 SSH 执行非交互脚本时，不一定加载用户终端里的 PATH；即使登录终端能用 `npm`，远程 `bash -s` 也可能找不到。部署脚本应显式补 `/opt/homebrew/bin:/usr/local/bin` 并检查 `command -v npm`。
- 部署脚本如果需要在远端通过 `./scripts/*.sh` 直接执行，必须把可执行权限提交进 git；只在本机 chmod 但没有形成 mode change，Mac mini 拉取后仍会是 `100644` 并报 `Permission denied`。
- 一键发布脚本里不要用 `git add -A -- ':!ignored-dir'` 排除已忽略目录；Git 可能把 ignored pathspec 当成错误。更稳的做法是先 `git add -A`，再用 `git reset -q -- path` 从暂存区移出数据库或备份目录。
- 小刘职责调整后只主责业务逻辑、API、文档、测试；部署、生产环境、发布流程、服务器、域名 HTTPS、进程管理、数据库生产化迁移等事项应反馈给老王或转给小张，不要主动接部署任务。
- 小刘会话收尾要克制：完成代码和职责内验证后，更新 `tasks/todo.md`，仅在确有长期规则或经验变化时更新 `摄影助理自动派单系统.md` / `tasks/lessons.md`，最后向老王汇报完成情况，不额外发散。
- 多角色协作时要先守住角色边界：小李负责 UI 但不改核心派单逻辑，小刘负责业务逻辑/API/文档/测试但不随便重做 UI、不主动接部署任务，小张负责性能/并发/数据库/架构/部署/生产环境但不改业务规则，最终合并和验收交给老王。
- API 查询边界和权限校验要分开处理：`limit/buildingId/view/includeCollaborators` 能降低百人轮询压力，但不能替代登录态、角色和本人/管理员权限校验。
- 快捷预约“指定助理”这种入口不能只靠前端筛人；`POST /api/tasks` 必须后端校验角色、在线状态和服务楼座，失败时直接 4xx，不回退自动派单。
- 指定助理不是普通自动派发候选筛选：可以指定已有待执行、执行中、暂停或协作任务的在线同楼座助理；后端不能用 `dispatchableAssistantIds()` 或 `Profile.status` 忙碌态直接拦截，也不能覆盖她当前执行状态。
- 暗黑主题适配不要只依赖全局 `.glass` 规则覆盖 Tailwind 工具类；左侧工作台这类主题敏感高层面板应加语义 class，必要时用 `resolvedTheme` 同步显式 dark class，避免 `bg-white/25` 等浅色工具类在构建顺序里抢优先级。
- 助理有“登记位置”和“实际服务位置”两套字段；工作台顶部、身份切换弹窗、地图/队列筛选这类运行视角应优先用 `activeBuildingId`，不要让 `buildingId/currentRoom` 覆盖切换后的真实服务地点。助理空闲态只显示楼座，不能自动把公共区域写入或展示成当前房间。
- 摄影师工作台位置也不能复用备案字段：跨楼座临时位置应放在页面本地状态中，发单用工作台楼座/场地，后台人员管理的 `buildingId/currentRoom` 保持不变。
- 一键启动器给非技术用户使用时，开发服务应优先在终端前台运行；隐藏后台 `nohup` 服务一旦异常或重复启动，用户很难发现和停止，容易造成内存持续上涨。
- Next 16/Turbopack 项目如果上级目录也有 lockfile，必须在 `next.config.ts` 固定 `turbopack.root` 到真实项目目录；否则开发服务可能监听整个移动硬盘工作区，引发不必要的内存和文件监听压力。
- 启动器健康检查应使用轻量接口，例如 `/api/config`；不要在等待循环里反复请求 `/photographer` 这类重量页面，否则启动阶段会重复触发编译和数据加载。
- macOS 双击脚本不要依赖系统未必自带的 `flock`；用 `mkdir` 目录锁更稳，并要记录 PID 以便清理异常退出留下的锁。
- Bash 里不要用 `HOSTNAME` 作为自定义配置变量；它可能被 shell 环境预置，导致 `next dev -H` 绑定到电脑名而不是预期的 `0.0.0.0`。
- 摄影师发布上限判断前必须先跑跨天过期任务清理；否则移动端今日任务列表为空，但昨天遗留的 `waiting/paused/executing` 仍会被计入未完成任务，造成“看起来没任务却不能发单”。
- Prisma schema 新增字段并 `prisma generate` 后，本地 Next dev server 可能仍持有旧客户端；涉及新增 Prisma 字段的 API 回归前需要重启 dev server。
- 区分“待就位让行”和“执行中插单”：前者是队列重排，不应复用任务类型可插单限制；后者才需要严格按后台可插单、30分钟内不可插单和最大离场时间配置执行。
- 新建任务即时派发和 `sweepWaitingTasks()` 后续扫描不能各自复制执行中插单筛选；优先沉到 scheduler 共用 helper，否则公共队列等待任务会漏掉后续自动插单，或与创建瞬间规则不一致。
- 不要用人员 `updatedAt` 推算业务状态持续时间；资料更新、楼座切换、在线状态切换都会刷新它。像“吃饭中计时/冷却”这种行为状态要有独立开始/结束时间，并在接口层强制校验。
- 身份切换弹窗里的小菜单要同时处理 `pointerdown`、`mousedown` 和 `click` 冒泡；只拦 `click` 容易出现菜单能展开但菜单项点不到或被外层行交互抢走。
- 判断助理是否“暂停中可切状态”时，要同时考虑主助理任务和 `TaskCollaborator` 协作任务；多人协作下只查 `bookingTask.assistantId` 会误判并拒绝状态切换。
- Next dev server 的服务端 HTML 可能在热更新后仍保留旧 Client Component 预渲染结果；遇到客户端已更新但 SSR class 仍旧、出现 hydration mismatch 时，重启 dev server 并清理 `.next` 后再做最终截图验证。
- 身份切换面板默认应该是“选择身份/查看状态”，不要让管理账号在这里直接代改助理业务状态；在线/吃饭/休假这类会影响派发的状态变更必须先校验当前身份本人。
- 自动适配视图的逻辑要区分“系统模式切换”和“数据刷新”：用户拖拽/缩放接管地图后，轮询刷新不应再强制覆盖 `zoom/pan`，只有楼座切换、抽屉开合这类明确模式变化才重置手动状态。
- 解决统计面板遮挡时，优先让面板回到 grid/flex 轨道内受布局约束；不要用脱离布局的 `absolute + min-width` 去“顶层显示”，否则会在窄窗口覆盖相邻区域，浮层类内容再单独用 fixed 并按视口夹紧。
- 在带 `transform` 动画的面板内部不要直接渲染 `position: fixed` 浮层；浏览器会把 transformed ancestor 当作 fixed 的包含块，导致坐标错位或看起来不显示。工具提示、明细气泡这类浮层应使用 Portal 挂到 `document.body`。
- 主题、时间、窗口尺寸、localStorage 等客户端专属值不要放进 `useState` 初始化函数参与首帧渲染；Next SSR 会用服务端默认值，客户端首帧如果直接读取本地值就会触发 Hydration mismatch。应先用稳定默认值，挂载后再读取并切换。
- 自动换人和自动离线必须解耦：待就位超时可以把该任务换给别人，但旧助理是否离线要先查她是否还有其他执行中/暂停中的主任务或协作任务，避免把正在工作的助理误判下线。
- 待就位超时离线不能只靠“切地点/发任务”触发；工作台轮询也要定期触发 `sweepWaitingTasks()`，否则超时换人和自动离线会长时间不跑。
- 待就位超时扫描不能在“当前无可替换助理”时静默跳过普通任务；如果当前负责人没有其他真实执行/暂停工作，应先把负责人置离线，并把普通待就位任务释放为公共队列，等待后续空闲助理继续派发。
- 待就位等待时长不能统一按任务 `createdAt` 算；已经转派后的等待应优先按当前 primary 的 `joinedAt` 计算，否则新负责人会背上旧负责人等待时间。
- 弹窗内表头要吸附到整个弹窗顶部时，不能让表格再包一层独立纵向滚动；同时要用 `elementFromPoint` 复核数字入口的真实命中层，避免后渲染的指标按钮覆盖点击区域。
- 大范围后台 UI 统一优先使用页面作用域外壳承接基础样式，再给表格、弹窗、浮层、工具条等高频组件加语义类；这样能降低影响前台工作台的风险。
- 自定义图片背景叠加毛玻璃时，不要靠取消透明感解决阅读性；优先加全局柔和遮罩、提高文字层对比和给关键 tooltip/按钮独立可读底色。
- 后台在线状态菜单不要同时提供“离线”和“休假/下班/离线”；业务上保留一个离开状态入口，旧数据里的 `offline` 只做展示兼容，不作为常规切换选项。
- Next/Turbopack 的 `.next/dev/cache/turbopack` 不耐受 macOS 在移动硬盘上生成的 `._*` 伴生文件；遇到 `Loading persistence directory failed` 时，优先清理 `.next` 缓存或删除 `._*`，不要先怀疑业务 SQLite 数据库。
- Next 16 开发服务用局域网 IP 给真机访问时，需要在 `next.config.ts` 配置 `allowedDevOrigins` 并重启；否则页面可能服务端 HTML 能出来，但客户端接管、接口刷新或点击事件表现异常。
- 手机真机和电脑 `localhost` 是不同 origin，身份共享不能依赖 `localStorage`；工作台这类多人系统应优先用 URL `profileId/employeeId` 承载当前身份，再落本地缓存。
- 移动端首帧不要用 `window.location`、`localStorage` 或窗口尺寸直接决定服务端/客户端不一致的文案；先用稳定加载态，挂载后再解析身份，避免 hydration mismatch 导致点击事件失效。
- 全站移动适配要显式输出 `viewport width=device-width, initial-scale=1`，尤其是要让真机浏览器和电脑设备模拟使用同一个 CSS 断点时，不要只依赖框架默认值。
- 任务状态里的 `waiting` 不是一个可直接展示的业务文案：没有分配人员时应显示“队列中”，已经分配但尚未开始时才显示“待就位”。
- 动态提权的公平性不能只看 `assistantId` 是否为空；已分配但尚未就位的 `waiting` 任务也还没真正开始，应该按等待时长参与提权，避免长期被公共队列新任务让行。
- 统计页口径要和实时工作台口径分开：后台「已完成超时」只统计 `completedAt > estEndTime` 的已完结任务；工作台「当前已超时」才看进行中/暂停中的实时超时。
- 任务转派必须先收敛旧参与记录：尤其是 `role=primary` 的任务只能保留一个当前主负责人。把新助理 upsert 为 primary 前，要把旧 primary 标记为 `left`；状态同步也要排除被动等待类任务，否则会把多个历史负责人误同步成待就位，并允许多人误开始同一主任务。
- 被动等待熨烫机不等于助理正在工作：派发、空闲判断、待就位让行、状态同步里都要排除 `waiting_machine/notified` 这类未开始占用机器的熨烫等待任务；待就位让行仍属于队列重排，不套用执行中插单的不可插单配置。
- 取消任务的硬边界是“助理是否已经点击开始/进入插单链路”：纯 `waiting` 可取消；`paused/executing`、插单子任务、已有未完成子插单的父任务都视为已进入执行流程，必须后端 409 拦截，前端不能乐观假删。
- 待就位超时换人不能吃掉未开始熨烫排队任务：`waiting_machine` 和历史口径里的 `waiting + 熨烫 + 已分配 + stage=none` 仍是机器队列，不该走普通待就位换人；只有 `notified` 准备熨烫超时未开始，才允许按换人阈值转派。
- 前台“当前任务状态”要展示可行动的下一步：`waiting_machine/notified` 熨烫等待不能抢占普通待就位任务的开始入口；只有没有其他可开始任务时，才把熨烫等待显示为不可点击提示。
- 任务状态卡片需要吃满剩余高度时，不能只给按钮本身 `h-full`；它的直接父级也要是明确的 flex 填充容器，避免按钮按内容高度显示、底部留下空白。
- 熨烫等待要区分 `waiting_machine` 和 `notified`：前者表示没有机器可用，当前任务卡可先展示其他待就位任务；后者表示机器已空/已通知准备熨烫，应优先让原负责人待就位熨烫。普通待就位任务只有在负责人真正开始熨烫后，才可以按超时等待规则转派给其他空闲助理。
- `notified` 是临时熨烫机使用权，不是真正开始使用机器：调度不能反复刷新 `ironingNotifiedAt`，必须有独立保护期；超时未开始要退回 `waiting_machine` 并让本轮下一条任务获得机器，避免单台机器被空占。
- 执行中插单不能只看优先级和离场时间：同楼座有熨烫排队压力时，正在执行熨烫任务的助理要受机器队列保护；API 候选筛选和 `canInterrupt()` 必须双层兜底，避免不同入口绕过。
- 助理状态栏不能把多个可行动任务压成单个 `current`：当普通待就位和 `notified` 准备熨烫同时存在时，应展示多个可点击入口；只有 `waiting_machine` 这种没有机器空位的熨烫等待才保持不可点击提示。
- `notified` 准备熨烫超时无人可换时不能静默跳过：如果本人没有真实执行/暂停工作，应把本人置为离线但保留任务归属，等待她回在线后自行选择开始；超时计时必须从 `ironingNotifiedAt` 开始，不能沿用排队或参与记录时间。
- 当前任务状态里只要有多个可行动等待任务，就必须进入同一个“选择要开始的任务”容器；不要把 `notified` 熨烫单独渲染成主卡，再把普通待就位渲染成 `1 个可选`，否则用户无法理解当前真实可选项。
- 熨烫机右上角头像和地图头像是两个并行状态维度：右上角表达机器接续/排队顺序，地图表达助理所在任务位置，二者不互斥；准备熨烫头像应同时出现在机器接续区和对应房间地图上。
- 熨烫机接续排队不能按固定机器号或简单轮询：有空闲机器时直接挂空闲机；机器全满时要按每台机器预计可用时间轴动态重算，排在前面的等待任务时长也要计入该机器后续可用时间。
- 通用待就位换人规则不要挂在熨烫配置里：配置、文案和运行时读取都应独立于熨烫机接续规则；扫描顺序应先处理可换人的 `notified/普通待就位`，再释放熨烫机使用权，避免超时准备熨烫任务被先打回等待机器队列。
- 派发候选不能只看 `profile.status=idle`：助理可能因为历史/普通待就位熨烫保持 `assigned`，但实际只有未开始熨烫等待；普通新任务、扫队列和自动认领都应按“是否存在真实占用任务/协作任务”判断可派发能力。
- 未开始熨烫等待不占用助理，但也不能无限集中在同一人身上：同楼座有空闲可派发助理时，应保留已获机器使用权的 `notified`，把额外的 `waiting_machine/stage=none` 熨烫等待自动均衡给没有熨烫等待的助理。
- 未开始任务可选择开始池不能只靠前端筛选熨烫机状态；`PATCH /api/tasks/[id] action=start` 必须同口径校验机器可用或 `notified`，并在临时接手其他负责人熨烫任务时收敛 primary 参与记录。
- 任务取消边界不能只看 `status=waiting` 或是否存在插单父子链路；真正的“是否已经开始”应以本任务 `startedAt` 为准。未开始的插单父任务可以取消并解除子任务父关联，已开始后让行/暂停再显示待就位的任务不能取消。
- 任务本体状态和参与记录状态必须定期收敛：如果全部当前参与记录已 `completed`，但 `booking_tasks.status` 仍停在 `waiting`，公共队列会误显示“已分配待就位”，而人员状态同步会显示空闲。维护扫描应先聚合任务状态，再同步人员状态。
- 工作台等价拆分时要先识别函数依赖边界：纯类型、纯展示和位置派生可以外移；依赖页面视觉常量或 JSX 状态的函数先留在页面内，避免为了“拆文件”反而制造反向依赖。
- 移动端 UI 组件拆分时，先把“是否可开始/取消/恢复/指定”等业务判断留在页面层或派生函数里；新组件只接收展示 props 和回调，避免 UI 可维护性拆分夹带派单逻辑变化。
- 纯 UI 浏览器验收直接打开工作台也可能触发页面既有轮询和 `/api/tasks/sweep` 维护写入；需要保护本地数据时，优先使用隔离测试库、只跑类型/构建验证，或临时关闭维护轮询后再截图。
- 依赖安全补丁要和业务改动分开：`next/eslint-config-next` 这类框架补丁可以单独升并跑 build/audit，但不要用 `npm audit fix --force` 把 Prisma、Next 或其它核心包跨大版本降级/升级。
- macOS `._*` 伴生文件清理脚本默认应 dry-run，并明确排除 `.git`、数据库备份、日志、上传资源和真实 SQLite；需要实际删除时再显式 `--apply`。
- 恢复 lint 可用性要先排除生成物、缓存、`._*` 和验证产物；随后把真实 lint 错误按规则类型拆批修，避免一次性重构 UI、业务和工具链。
- 助理“可开始任务池”里同类熨烫任务要先收敛为一条最推荐任务；机器空闲提示属于时长/建议说明，不应和「准备熨烫」业务状态标签混在一起。
- 同一页面同时维护任务列表、当前任务和展示卡片时，操作成功后要先统一收敛本地状态，再异步拉后端校准；不要只依赖轮询，否则会出现列表已更新但顶部状态仍显示旧候选的延迟感。
- 人工提权申请和自动等待提权要分开建模：人工申请需要独立审批记录，审批通过后再写任务 `priority/escalatedAt/escalatedFromPriority`，避免申请态污染自动提权和公共队列排序。
- Prisma schema 新增关系后，即使 `prisma generate/db push` 成功，正在运行的 Next dev server 仍可能持有旧 Prisma Client；如果 `/api/tasks` 报 unknown field 这类错误，必须清理 `.next` 缓存/`._*` 伴生文件并重启服务。
- 涉及按钮显示权限的后台配置必须前后端同口径：摄影师端可以隐藏「申请提权」，但提交 API 仍要读取同一配置兜底拦截，避免绕过前端直接调用接口。
- 完成后的复盘/异常登记数据应独立建模，不要堆进 `BookingTask` 主表；这类数据用于统计追踪，不应反向影响派单排序、任务状态或优先级。
- 熨烫机容量不能按熨烫任务条数计算；多人协作熨烫是一人一机，调度、开始接口、`notified` 预占和前端可视化都要按主助理 + 未退出/未完成协作者的机器槽位数统一计算，暂停参与者仍占用机器。
- 前端判断任务是否属于当前助理时，不能只看未 `left` 的 `TaskCollaborator`；`role=primary` 必须以主任务 `assistantId` 为准，只有 helper/协作者才可直接按参与记录归属，避免转派后旧助理继续看到「点击开始」。
- 摄影师工作台要区分“地图浏览楼座”和“发单服务楼座”：地图切换只影响区域看板/地图，只有头像名片地址切换才改变快捷预约发布位置和指定助理候选范围。
- 取消任务属于发布者权限，不是助理操作；前端隐藏助理取消入口的同时，后端删除接口也必须校验操作者是该任务摄影师。
- 任务状态聚合不能让历史 `primary` 参与记录参与当前状态判断；同一任务只允许当前 `booking_tasks.assistant_id` 对应的 primary 影响主任务状态，旧 primary 应先标记 `left`，否则已完成插单会被旧 waiting 记录拖回「插单等待中」。
- 多人协作是现场人力需求，不是任务时长属性；不要用 `maxDuration > 30` 之类时长门槛隐藏协作入口或拦截接口，短任务也可能需要多人同时完成。
- 吃饭状态要区分“暂停”和“结束”：暂停只累计本段吃饭秒数并回在线，不写结束时间、不触发冷却；只有明确结束吃饭才写 `eatingEndedAt` 并进入再次切换冷却。
- 暂停吃饭必须有独立的 `eatingPausedAt` 暂停开始时间；不能用 `updatedAt` 或“暂停到继续的间隔”推算吃饭累计，否则暂停几个小时后会被误判超过吃饭上限。
- 助理状态切换要按“是否真正开始工作”判断：未开始的 `waiting/待就位` 可释放回队列后切换吃饭/休假，`executing/finishing` 或已开始后暂停才属于不可直接释放的真实工作。
- 工作台里的状态切换提示要统一使用页面中心轻提示/确认框；不要混用浏览器原生 `confirm/alert` 或顶部小条，避免手机端和桌面端交互不一致。
- 外模跟拍协助虽然可从「其他」快捷入口发布，但展示统计不能继续显示为「其他」；综合分明细、后台数据和任务类型占比都要统一显示「外模跟拍协助」，并兼容 `P6 + 其他` 的快捷回退任务。
- 助理“我的任务”列表应以查看为主，不能把待就位/进行中/暂停中状态标签混成开始、完成、暂停入口；任务操作集中放在“当前任务状态”面板，已完成登记入口是例外。
- 低优先级不等于一定可被插单：外模跟拍协助虽然是 P6，但工作模式是全天跟拍，执行中必须作为不可插单任务保护。
- 暂停吃饭后助理可以回到在线可派发，但本次吃饭还没有结束；当前任务状态区应保留低高度“吃饭已暂停”短条，不能完全显示成普通空闲状态。
- 主助理移交不能只改 `booking_tasks.assistant_id`：必须结算旧主助理工时、旧 primary 标记 `completed` 作为该任务贡献记录、新 primary 写入 `waiting`，并同步双方人员状态；旧助理不能继续操作已移交任务，但她的完成贡献不能丢。
- 忙碌助理之间的任务互换要结构化记录 `kind/responseMode/counterpartTaskId`，不要把“暂停并前往/结束后前往”塞进 `reason`；马上互换必须一个事务内处理两条任务和两边 primary，结束后前往应先进入 `ready_to_takeover` 通知原助理，等目标助理点击开始接替时再切换主负责人并释放原助理。
- 空闲移交也不能在目标确认时释放原助理；确认只应进入 `ready_to_takeover` 并让目标助理显示待就位，目标助理点击开始接替后才执行主负责人切换和原助理释放。
- 移交/互换时交出任务的一方不能标记为 `left`，否则任务完成贡献和综合分会丢失；应把该参与记录结算为 `completed`，再让新负责人以新的 `waiting` primary 接手。
- 百人高强度工作台不能让每个客户端周期性触发全局 sweep；应由写接口和服务端节流同步入口集中维护，否则读刷新会放大成写锁压力。
- 自动派发不能只在事务前选人；事务内必须再次确认任务仍未分配、助理仍在线同楼座且无真实占用任务，认领失败就换候选，避免并发重复派单。
- 助理手动开始任务必须有后端优先级兜底；前端排序和置灰只是体验，服务端要拒绝绕过更高优先级可开始任务。
- SQLite 百人试运行前要设置 WAL、busy_timeout 和 synchronous=NORMAL，并保持单 Node 进程写库；不要用多个服务实例同时写同一个 SQLite 文件。
- 单任务 PATCH 不能在后端用 `task.assistantId` 兜底 actor；否则调用方不传身份也会被当作当前助理。开始、暂停、完成、移交都必须显式传 actor，并在服务端校验角色和当前参与关系。
- `setStatus` 这类调试入口不能保留执行态直写能力；哪怕只给管理端，也会绕过优先级、熨烫机槽位、参与者和计时结算规则。执行/暂停必须走原子命令。
- 写操作成功后前端应立即合并后端权威任务详情，并让短时间内的旧轮询快照让位；否则弱网或乱序响应会把 waiting/executing/completed 状态闪回。
- 从后台切回工作台前台时要立即同步一次；只在下一轮隐藏态定时器到点后刷新，会让现场状态最多滞后一个隐藏轮询周期。
- 正式压测要先使用隔离 SQLite 库和独立端口跑 smoke，再跑只读和混合基线；压测库、WAL/SHM 和结果目录必须进 `.gitignore`，不要把 `prisma/dev.db` 或 Mac mini 生产库拿来做混合写压测。
- 百人只读场景即使 HTTP p95 很低，也可能因为 `/api/workbench/sync` 返回重快照而产生巨大网络和前端解析压力；本轮 115 会话 10 分钟产生约 2.17GB 同步响应体，优化优先级应看响应体体积和前端合并成本，不只看接口延迟。
- 混合压测中业务 409 要和系统错误分开统计：高优先级兜底、摄影师发布上限、熨烫机忙属于正确拦截；真正需要追查的是 500、SQLite locked/busy、重复 primary、多活跃根任务和机器槽位超占。
- 熨烫派发/开始必须作为原子状态命令收口；本轮混合压测复现了同一助理多个活跃根熨烫任务、楼座 `using` 数超过机器数量的问题，证明事务外计算槽位再写入在高并发下不够安全。
- SQLite 单进程阶段遇到“按楼座计算剩余熨烫机槽位再写入”的聚合约束时，光靠事务读后写还不够直观；应在 Node 进程内按楼座串行化槽位计算和写入，同时保留事务内二次校验。迁多进程或 PostgreSQL 前必须重新设计为数据库级锁/约束。
- `notified` 准备熨烫不是普通待就位：等待机器期间可以先接普通任务，但一旦助理已有执行中/暂停中真实工作，开始熨烫必须拒绝，否则会出现同一助理同时执行普通任务和熨烫任务。
- `/api/workbench/sync` 的“大数据量”主要是累计同步响应体，不是数据库落盘文本；几十 KB 的 JSON 被上百客户端每 2-3 秒重复拉取，一天会放大到百 GB/TB 级。优化要优先做摘要/增量和服务端聚合，单纯压缩字段只能缓解网络，不能减少前端解析成本。
- 增量同步压测必须让每个虚拟用户像真实前端一样保存 `syncToken` 和本地任务缓存；如果压测脚本每轮都不带 `since`，服务端和前端即使已支持 delta，报告仍会被全量快照污染。
- `since` 增量同步要配合当前可见 ID 列表裁剪本地缓存，并定期强制全量校准；只传变更任务而不传可见 ID，会让已完成、转移楼座或归属变化后不再可见的任务长期残留在前端。
- 当增量同步已有 token、可见 ID 裁剪、截断重拉和缺失详情重拉时，定时 full 校准不应过密；60 秒 full 会把 p95 bytes 推回大包级，5 分钟 full 更适合把全量对账保留为保险而不是主同步路径。
- 服务端展示摘要不能从公共队列窗口截断推导；助理状态这类权威展示源必须单独查询完整相关任务、补齐父任务闭包，做不到完整时宁可不返回摘要并让前端回退旧逻辑。
- 混合压测里的预期业务 409 不应当按系统异常打印错误栈；高优先级兜底、已有执行/暂停任务、熨烫机槽位和移交资格拒绝应保留 409 响应，但从 `console.error` 中降噪，避免高并发时日志 IO 和误报排查成本放大。
- 高频同步里的服务端摘要要返回“补丁”而不是完整对象；`null/false/0` 这类默认值每 3 秒乘以上百客户端会变成固定流量，只有会覆盖基础 profile 的字段才值得下发。
- 工作台页面级 `now` 不应每秒刷新；秒表、吃饭计时、顶部时钟和即时状态点应拆成局部计时组件，列表/统计/队列按分钟或数据变更刷新，避免整页 React tree 在百人高频使用时被秒级重绘拖慢。
- 高频任务操作需要“同步 ref 拦截 + React state 反馈”双层 pending：ref 负责在同一事件循环内挡住重复点击，state 负责让按钮立即禁用并显示处理中；只做其中之一都会留下弱网重复提交或用户误点风险。
- 弱网/轮询并发下，操作成功后的权威任务合并不能读取旧 React 闭包数组；应以同步维护的 refs 作为当前任务源，并用短 TTL recent patch 保护刚操作的任务，避免旧快照闪回。
- 地图拖拽/缩放这类高频交互不要每个 pointer/wheel 事件都 `setState`；应把即时 pan/zoom 放进 ref，用 `requestAnimationFrame` 直接更新地图 transform，手势结束或滚轮停顿后再提交 React 状态。
- Dock 这类密集头像 hover 不需要 React 状态驱动 tooltip 和阴影；用 CSS `group-hover` 处理显隐/层级/视觉反馈，鼠标移动曲线只用 rAF 合并坐标提交，能减少扫过多名助理时的无意义重渲染。
- 工作台单任务局部补丁不要在每个操作里手写多组 `setTaskListRaw/setCurrentRawTask/setPublicQueueRaw`；应统一 helper 同步 raw refs、当前卡片、公共队列和展示列表，否则很容易漏掉让行任务或公共队列导致局部 UI 不一致。
- 工作台创建/取消这种插入删除路径也要同步 raw refs 和展示列表；只更新 `tasks` 或只更新 `taskListRaw` 会让下一次本地合并、临时卡回滚或公共队列校准读到不一致的状态。
- 移交/互换这类会改变“当前身份是否仍可见”的任务更新不能套普通单任务补丁；应集中用可见性 helper 同步 raw refs、当前任务卡和展示列表，并用按身份生效的短 TTL 隐藏保护挡住旧轮询闪回。
- 有动画前摇的高频写操作也要从点击瞬间进入 pending，而不是等动画结束或接口开始后再锁；否则快速连点会在动画期排队触发多次真实写入。
- 工作台本地 store 要从已经稳定的子域开始抽：pendingActions 这类只有键集合和同步 ref 拦截的状态适合先独立成 hook，再逐步推进更复杂的 tasksById/profilesById。
- optimistic patch 和 hidden TTL 属于同一套闪回保护，必须集中在一个 hook/store 里同时清理过期项；分散在页面里会让权威快照、移交隐藏和乐观开始/完成互相绕开。
- 抽任务源列表纯函数时要保留原有列表顺序语义：有的路径是原位合并避免状态卡闪动，有的路径是先删再追加匹配临时任务替换；统一 helper 必须显式表达这些差异。
- 全量快照和乐观补丁重新解析当前/暂停/pending 任务后，要同步更新对应 ref；只等 React state 提交会让同一事件循环内的弱网连续操作读到旧任务源。
- Mac mini 发布脚本只要临时保护过生产 SQLite，就必须用 `trap` 兜底恢复；否则远端 stash、pull 或 build 中途失败时，可能把 `prisma/dev.db` 停留在仓库版本而不是生产库。
- `git stash push -u` 不要混用被忽略目录的 exclude pathspec 来处理远端脏工作区；被 `.gitignore` 忽略的 `database-backups/logs` 可能让 stash 直接失败，生产部署更稳的做法是先保护数据库，再 stash 非忽略变更。
- 工作台 `tasksById` store 第一批应先接管一个主任务源，并保留同步 ref；弱网连续操作、轮询乱序合并和乐观补丁路径需要先读 ref 再等 React state 更新。
- 多任务源 reducer 化不要一次迁完 `taskListRaw/assistantRawTasks/publicQueueRaw`；先迁主源、验证全量应用和局部补丁，再迁助理源和公共队列，能降低状态卡片、列表和地图同时闪动的风险。
- 当 store 方法会同步更新 ref 时，分支判断必须先保存调用前状态；例如 `assistantRawTasksRef.current.length` 在 `upsert/replace` 后会立即变化，不能再用它判断操作前是否为空。
- 替换数组 `find()` 时要区分 id 索引查找和业务条件筛选：`id -> task` 可以走 store，移交请求/开始候选池这类条件筛选先保留数组逻辑，避免性能优化夹带规则变化。
- 公共队列这类跨角色共享任务源也要接入同一 reducer/store；否则局部补丁、同步合并和动画读侧会继续分散维护 `setState/ref`，后续做摘要化或索引化时容易漏掉一个写入口。
- 排序 comparator 里不要临时扫描或构建队列上下文；暂停插单、公共队列状态这类派生信息应先一次性建 lookup/map，再供排序、动画推断和卡片渲染复用。
- 图片/背景这类大字段不要直接放进通用配置 JSON 默认响应；通用配置应返回轻量 URL/元信息，原始大值只在明确按需读取或专用媒体路由中返回。
- 工作台共享索引只替换纯 `id -> object/name` 查找；`employeeId` 登录恢复、协作候选、楼座列表过滤这类条件筛选应保留原遍历或单独建专用索引，避免性能优化改变业务口径。
- 后台统计页不要默认拉取全量深任务历史；按当前日期窗口请求，并为统计场景提供专用轻量 payload，能避免一天/多天数据积累后后台打开即解析大量无关关系。
- Prisma 的 `include` 会默认带出模型全部标量字段；面向统计、摘要、列表这类轻量接口时应使用 `select` 明确字段，否则即使裁掉关系，仍会传输大量页面不用的任务标量。
- 高频同步里的人员资料也必须显式 `select`；默认整行返回会把 `password/avatar` 这类无关或大字段混进 2-3 秒轮询。头像这类图片字段应改成可缓存 URL/专用图片路由，不能作为 base64 JSON 跟随每轮同步。
- profile 这类会被多页面复用的 API 出口要集中做公开序列化；不要让每个路由各自手写“删 password / 转头像 URL”，否则新增入口很容易再次泄露无关字段或大字段。
- 同一个列表接口被身份选择、后台管理和统计页复用时，应提供场景化 `view`；默认兼容旧字段，页面显式请求轻量 view，能在不改业务规则的前提下降低首屏 JSON 和解析成本。
- 工作台非主同步的兜底刷新也必须带楼座范围；即使主轮询已经走增量同步，切楼座、切状态、任务操作后的 `/api/tasks?todayOnly=true` 如果不带 `buildingId`，仍会把全场今日任务作为大包拉回前端。
- 周统计弹窗不要复用任务详情深 payload；只做数量、趋势和明细表时应请求 `payload=stats`，区域统计再叠加 `buildingId`，把关系体积和 JSON 解析成本压到当前视图所需范围内。
- 管理员周期巡检列表不要复用任务详情 payload；即使 `includeCollaborators=false`，提权、移交、完成登记和多余标量仍会形成固定大包，应使用 `payload=adminList` 这类摘要视图，详情按需再拉。
- 楼座这类基础字典也要按场景拆 view：后台筛选和统计只需要 `id/name`，不要默认拉房间、熨烫机、平面图和裁剪字段；真正需要地图编辑时再按需拉 full。
- `<img src>` 可以直接消费短 URL 时，不要把平面图、背景图、头像这类 base64 大字段塞进 JSON；保留数据库兼容写法，但 API 出口应转成可缓存图片路由，减少网络和 JSON 解析压力。
- 高频工作台读同步不应 `await` 全局维护扫描；读请求只负责触发服务端节流后台维护并尽快返回当前快照，写操作和显式 sweep 继续负责强一致维护，避免百人轮询被维护等待放大成尾延迟。
- 压测里的 HTTP 409 必须按业务原因分类看：摄影师发布上限、高优先级兜底、已有真实工作不能开始熨烫等是正确拦截；判断系统是否冲突要看 500/timeout/SQLite locked、不变量破坏和重复派单，而不是只看 409 数量。
- 压测脚本的助理动作选择要模拟真实 UI 可行动作，不能简单按 `waiting -> paused -> executing` 顺序点；已有执行/暂停真实工作时继续点熨烫 start，只会制造后端正确拒绝的 409，污染吞吐和体验判断。
- 降低业务 409 不能只看错误数下降；每次减少前端/压测无效请求后都要复查状态不变量。普通根任务开始必须后端事务内兜底“当前助理无其他执行/暂停真实工作”，结构化插单用 `parentTaskId` 单独放行。
- 摄影师端已经有发布上限个人队列任务时，前端和压测都应本地预检并阻止重复发单；后端 `PHOTOGRAPHER_LIMIT_QUEUE_FULL` 继续作为权威兜底，但不应让重复 409 写请求代表真实工作负载。
- 助理可开始任务池要按后端最高优先级兜底同口径裁剪；前端和压测只展示/点击当前最高优先级候选，后端仍保留权威 409 处理同步滞后、并发新任务和绕过 UI 的请求。
- 高频同步里的实体基础资料适合“首轮 full + 后续 delta 补丁”；前端收到补丁时必须合并到既有完整列表，再叠加状态摘要，不能把补丁数组当成完整列表直接替换。
- 定时 full 校准是保险而不是主同步路径；在 delta 有可见 ID 裁剪、截断重拉和缺失详情重拉兜底后，可以适度降频，但不能移除首轮 full、身份/楼座切换 full 和异常立即 full 重拉。
- 工作台区域统计要先做服务端权威摘要，再裁剪高频任务详情；不能直接把 completed 或历史任务从 `publicQueue` 里删掉后继续让前端本地统计，否则区域完成数、任务类型占比和助理排行会被裁小。
- 服务端摘要也不能无脑每轮 delta 完整下发；只读场景里摘要不变时应让前端复用上一份，只有 full 或相关任务/关联记录变化时再下发，否则“摘要化”会变成新的固定轮询大包。
- 高频摘要里的排行总分和任务明细要分开建模：总分/完成数/工时必须按全量贡献计算，任务明细可以不随同步默认下发；不能为了裁剪明细让排行只按最近几条任务计分。
- 增量同步瘦身要区分 full 和 delta：full 快照可以省略 null/false/空数组这类默认值，因为会整体替换本地可见集；delta 补丁必须保留 null/false/空数组清空语义，否则旧字段会残留。
- 高频同步里的状态摘要可以按变化和时间桶下发：无变化 3 秒 delta 应复用前端上一份状态，区域任务/人员变化或跨分钟时再校准，避免把 Dock/地图状态变成固定广播包。
